- ขั้นตอนทดสอบด้วยมือ (ทำซ้ำได้):
  1. login เป็น creator → เปิด `/studio/connections` → ต้องเห็นสถานะว่างพร้อมปุ่ม "เพิ่มการเชื่อมต่อ"
  2. เพิ่ม PostgreSQL ที่ host `127.0.0.1` → กดทดสอบ → ต้องได้ข้อความภาษาไทยว่าไม่อนุญาต host ภายใน (AC4)
  3. สร้าง role อ่านอย่างเดียวบน DB ทดสอบ (`CREATE ROLE ro LOGIN PASSWORD '...'; GRANT CONNECT ...; GRANT USAGE ON SCHEMA public ...; GRANT SELECT ON ALL TABLES IN SCHEMA public ...`) → กรอกในฟอร์ม → ทดสอบ → ต้องขึ้นสีเขียว "อ่านอย่างเดียว" → บันทึก → สถานะ "ใช้ได้" (AC1)
  4. ใช้บัญชี owner → ทดสอบ → ต้องขึ้นกล่องสีแดง และปุ่มบันทึกกดไม่ได้จนกว่าจะติ๊กยืนยัน (AC2)
  5. DevTools → Network → `GET /api/studio/connections` → ต้องไม่มี `password` มีแค่ `hasPassword` (AC3)
  6. กด "ดู schema" → เลือกตาราง → ต้องเห็นคอลัมน์ และตัวอย่างไม่เกิน 5 แถว (AC5)
  7. ผูก connection กับ knowledge_source แล้วกด "ลบ" → ต้องเห็นชื่อ Knowledge Set และ API ตอบ 409 (AC6)
  8. แก้ไข connection โดยเว้นรหัสผ่านว่าง → ต้องบันทึกได้ แต่ถ้าเปลี่ยน host/port แล้วเว้นรหัสผ่านว่าง ต้องได้ 400
- สิ่งที่เบี่ยงจาก Spec + เหตุผล:
  1. **ใช้ helper ของกลางแบบชั่วคราว** (`lib/studio/connections/core-shim.ts`: `encryptSecret`/`decryptSecret`, `logActivity`, `jsonError`) เพราะ CORE-01 ยังไม่ merge ตัว signature ทำตาม spec ของ CORE-01 เมื่อ CORE-01 เข้าแล้วให้ลบไฟล์นี้และเปลี่ยน import มาใช้ของกลาง ⚠ รูปแบบ ciphertext (`v1:iv:tag:data` และ key = SHA-256 ของ `STUDIO_SECRET_KEY`) อาจไม่ตรงกับของ CORE-01 ถ้าไม่ตรง ต้องให้ผู้ใช้กรอกรหัสผ่านใหม่
  2. **ตรวจ read-only ด้วย privilege แทนการสร้าง temp table** เพราะ PostgreSQL ให้สิทธิ์ TEMP กับ PUBLIC โดยค่าเริ่มต้น การสร้าง temp table สำเร็จจึงบอกไม่ได้ว่าเขียนข้อมูลจริงได้ จึงตรวจ superuser/createrole/createdb, CREATE บน database/schema และ INSERT/UPDATE/DELETE/TRUNCATE บนตาราง (Spec เปิดให้ "หรือตรวจ privilege" อยู่แล้ว)
  3. **บังคับเรื่องยืนยันบัญชีที่เขียนได้ที่ฝั่ง server ด้วย** POST/PUT จะทดสอบใหม่ทุกครั้ง ถ้าบัญชีเขียนได้และไม่ได้ส่ง `acknowledgeWritable: true` จะตอบ 409 `{ code: 'writable' }` สถานะที่บันทึกมาจากผลทดสอบของ server ไม่รับจาก client
  4. **ใช้รหัสผ่านเดิมได้เฉพาะเมื่อ server เดิม** เปลี่ยน type/host/port แล้วเว้นรหัสผ่านว่างจะได้ 400 เพื่อกันการแก้ host ให้ไปชี้ server ของผู้ไม่หวังดีแล้วดักรหัสผ่านเดิม
  5. **creator เห็นเฉพาะ connection ที่ตัวเองสร้าง** ส่วน admin เห็นทั้งหมด (ตามกติกา "กรองด้วย user_id ของ session") ถ้าทีมต้องการให้ creator ใช้ร่วมกัน ต้องตัดสินใจเพิ่ม
  6. **รองรับ MySQL และ SQL Server แล้ว (2026-10-25)** ผู้ใช้อนุมัติในแชทให้ติดตั้ง `mysql2@^3.24.6`, `mssql@^12.7.11`, `@types/mssql` (dev) **PR นี้จึงแก้ `package.json` / `package-lock.json` ซึ่งเป็นไฟล์ของ Maintainer ต้องให้ Maintainer review** และ `next build` ผ่านโดยไม่ต้องแก้ `next.config.ts`
     - MySQL (`drivers/mysql.ts`): ตรวจ read-only จาก `information_schema.*_PRIVILEGES` ของ `CURRENT_USER()` ถ้ามีสิทธิ์นอกเหนือจาก USAGE, SELECT, SHOW VIEW, SHOW DATABASES, LOCK TABLES, PROCESS, REPLICATION CLIENT หรือมี GRANT OPTION จะถือว่าเขียนได้ ทำงานใน `START TRANSACTION READ ONLY` และแสดงเฉพาะตารางของ database ที่เชื่อมต่อ ข้อจำกัด: สิทธิ์ที่ได้มาจาก role ของ MySQL 8 อาจไม่ปรากฏใน information_schema
     - **เพิ่มอีก 5 ประเภท รวมเป็น 8 (2026-10-25)** ผู้ใช้อนุมัติในแชทให้แก้ `ConnectionType` ใน `lib/studio/types.ts` (ของ CORE-01) และ CHECK constraint `data_connections_type_check` ใน DB ของ `.env` ให้รับ `postgresql, mysql, mssql, mariadb, cockroachdb, redshift, oracle, clickhouse` และติดตั้ง `oracledb@^26`, `@clickhouse/client@^1.24`, `@types/oracledb` (dev)
       - MariaDB → ใช้ driver ของ MySQL • CockroachDB → ใช้ driver ของ PostgreSQL (ตัด schema `crdb_internal`/`pg_extension` ออก และถือว่าจำนวนแถว 0 = ไม่ทราบ)
       - Redshift (`drivers/redshift.ts`): ใช้ pg แต่อ่าน catalog ผ่าน `information_schema` และ `pg_user` **ยังไม่ได้ทดสอบกับ cluster จริง**
       - Oracle (`drivers/oracle.ts`): thin mode (ไม่ต้องลง Oracle Client) ช่อง database คือ service name ใช้ `SET TRANSACTION READ ONLY` ถ้ามี system privilege นอกเหนือจาก CREATE SESSION/SELECT ANY…, เป็นเจ้าของตาราง หรือมีสิทธิ์ INSERT/UPDATE/DELETE/ALTER ผ่าน grant หรือ role จะถือว่าเขียนได้ SSL: disable/prefer = TCP, require/verify-full = TCPS
       - ClickHouse (`drivers/clickhouse.ts`): ใช้ HTTP interface ถ้า profile ตั้ง `readonly` ไว้ = อ่านอย่างเดียว ไม่อย่างนั้นจะ parse `SHOW GRANTS` (ทุกบัญชีดูของตัวเองได้ ต่างจาก `system.grants`) ถ้ามี role ที่ตรวจไม่ได้หรือมี GRANT OPTION จะถือว่าเขียนได้ SSL: disable/prefer = HTTP, require/verify-full = HTTPS
     - SQL Server (`drivers/mssql.ts`): ตรวจว่าเป็น sysadmin, db_owner, db_datawriter, db_ddladmin หรือมีสิทธิ์ INSERT/UPDATE/DELETE/ALTER/CREATE TABLE บน database หรือตาราง (`HAS_PERMS_BY_NAME`) ไม่มี READ ONLY transaction จึงใช้ transaction ที่ rollback ทุกครั้งร่วมกับ SELECT อย่างเดียว ส่วน `prefer` และ `require` ยอมรับใบรับรองแบบ self-signed
  7. **preview รับ `?schema=` เพิ่ม** (ค่าเริ่มต้น `public`) เพราะชื่อตารางซ้ำกันข้าม schema ได้ ชื่อตาราง/schema ต้องตรงกับตารางที่มีอยู่จริงและอ่านได้ก่อน จึงจะ quote แล้ว `SELECT * ... LIMIT 5` ภายใน transaction `READ ONLY`
  8. SSRF: resolve DNS ครั้งเดียวแล้วต่อไปที่ IP ที่ตรวจแล้ว (กัน DNS rebinding) บล็อก 0/8, 127/8, 169.254/16, `::1`, `fe80::/10`, `fd00:ec2::254` และ IP ของ interface ในเครื่อง server allowlist ตั้งผ่าน env `STUDIO_DB_HOST_ALLOWLIST` (คั่นด้วย comma)
- การเปลี่ยนแปลงกับ DB ใน `.env` (ผู้ใช้สั่งให้ทำในแชท 2026-10-21 ซึ่งขัดกับ D-004 / AGENTS.md):
  - สร้างตาราง `data_connections`, `knowledge_sets`, `knowledge_sources`, `activity_logs` และ index ด้วย `CREATE TABLE/INDEX IF NOT EXISTS` ตาม DDL ใน `docs/specs/00-data-model.md` (เพิ่ม index `knowledge_sources (connection_id)`)
  - เพิ่ม `STUDIO_SECRET_KEY` (สุ่ม) ลงใน `.env` ในเครื่อง ทีมที่ใช้ DB เดียวกันต้องใช้ key เดียวกัน ไม่อย่างนั้นจะถอดรหัสผ่านที่บันทึกไว้ไม่ได้
  - ข้อมูลทดสอบ (connection และ knowledge set) ลบแล้ว เหลือแถวใน `activity_logs` ของการทดสอบ
